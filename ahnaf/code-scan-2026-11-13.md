## 1. What the project is

**Kiln Watch** — NASA Space Apps 2026 challenge *"Harmonization of MODIS and VIIRS Hot Spots"*.
It harmonizes NASA FIRMS MODIS (Terra/Aqua) and VIIRS (Suomi-NPP/NOAA-20/NOAA-21) hotspot detections onto one
**"Aqua MODIS scale"**, so the 2000→present fire record does not jump when satellites arrive or end.

```
FIRMS (public Portolan GeoParquet mirror, CC0, no key)
  → server/kw/firms.py      DuckDB reads only the area's rows  → data/cache/<area>/<year>.parquet
  → server/kw/build.py      calibrate → stitch → validate      → data/regions/<area>/*.json
  → server/kw/science.py    all statistics (stdlib only)
  → server/kw/tools.py      one deterministic tool layer
       ↙         ↓           ↘
   api.py    mcp_server.py   agent.py      (FastAPI / 31-tool MCP / Gemini)
       ↓
   web/src   React 19 + MapLibre GL JS
```

### Verified correct — do not touch

The core-science pass checked these specifically and they are right. Recording them so they are not "fixed" later.

- **`science.seasonal_mann_kendall`** (`science.py:179-213`) — Monte-Carlo type-I error **4.9 %** at α = 0.05
  (12 seasons × 20 years), full power for a 0.5σ/yr trend. `S = Σ_j S_j` over within-season pairs and
  `var = Σ_j Var(S_j)` are consistent; tie correction is applied within season; `tau = S/Σ pairs_j` is the seasonal
  Kendall tau; the Sen slope is the median of all within-season pairwise slopes.
- **`science.combine`'s weighting machinery, apart from S1** — the returned variance `1/W` is exactly `Σ w²v` for
  normalised inverse-variance weights; `cv·(mu/v)` is the correct delta-method evaluation of the Poisson variance at
  the pooled mean; `mu²·s2` is the right conversion of a log-space calibration variance to an absolute one.
- **`science.ratio_calibration`** (`science.py:56-93`) — ratio-of-totals per calendar month, normal-normal
  empirical-Bayes shrinkage with `λ = τ²/(τ²+v)` on the log scale, `σ²` as extra-Poisson variance with a sane floor
  and a documented wide prior for < 3 co-observed months. (The `tau2` estimator is biased upward by ≈ mean(v)/12
  because it centres on the pooled log-ratio rather than the sample mean of the monthly log-ratios — worth a comment,
  not a change.)
- **`science.periods` / the ISO-week key alignment** — all 1359 weekly keys from `2000-W44` to `2026-W46` are
  contiguous, no gaps or duplicates; DuckDB's `week()`/`isoyear()` are both ISO-8601 and agree with Python's
  `isocalendar()`, so `PKEY` (`build.py:172`) and `sc.week_key` line up; `sc.calendar_month` (Thursday's month) is
  applied consistently everywhere.
- **`science.versus_history`** — partial periods are excluded from everyone's baseline but still scored; rank /
  percentile / median definitions are consistent; recency weights use the ISO year for weeks and the calendar year
  for months, matching `season_index`.
- **`_coverage`'s span clipping** — `min(b, through)` correctly shortens the last (partial) period; `partial` is
  flagged consistently for monthly and weekly.
- **`_chain`** (`build.py:227-235`) — per-link betas compose multiplicatively and σ² additively along the chain; the
  `LINKS` order guarantees each reference is already resolved.
- **`quantiles` / `quantile_map` / `wasserstein2`** — linear-interpolated order statistics, monotone mapping with an
  explicit out-of-support flag, W2 for equal-probability quantile vectors; `quantile_map` correctly refuses
  non-monotone / non-finite inputs.
- **`_trends`** — `None` values are filtered inside `seasonal_mann_kendall`; the "full" span (2001 → last complete
  year) deliberately drops the 2-month 2000 stub.
- **`outlook_cell` / `warning_level`** — quantiles are correct (`q[5]` = median, `q[9]` = p90 over 11 points), zeros
  are included in the climatology, and the "insufficient" guards (≥ 10 prior years, ≥ 100 typical-year hotspots,
  ≥ 5 hotspot scale) are all wired up correctly in `tools.early_warning`.
- **EONET `bbox` ordering** in `news.py` — the code sends `(w, n, e, s)`; EONET documents
  `(minLon, minLat, maxLon, maxLat)`, but EONET normalises min/max per pair. Measured: identical result sets for an
  asymmetric box (137 events either way; a lat/lon-swapped box gave 69, confirming the documented order). Harmless.
- **No SSRF, no committed secrets** — every outbound URL uses a fixed host with encoded parameters; `.env`,
  `data/alerts.json` and `data/cache/` are gitignored, and nothing in `data/` matches a secret pattern.

## 3. Findings — A. Harmonization science

### S1 · CRITICAL · `science.combine`: the weight function is discontinuous and inverted at zero, so a sensor that detected *nothing* wins the vote **[V]**

`server/kw/science.py:108` · `server/kw/build.py:213` · `server/kw/build.py:279-281`

```python
counting = cv * (mu / v) if v > 0 else cv      # science.py:108
```

For `v > 0` this evaluates the sensor's Poisson variance **at the pooled mean** — correct. For `v == 0` it falls back
to `cv` = `b²/c²`, i.e. the variance of *one* detection (because `_value` floors the count at 1:
`return v, max(v, 1.0)`, `build.py:213`).

So the weight **jumps up** as a sensor's reading crosses zero: a sensor reading 0.01 gets variance `b·mu/c` (large →
low weight), a sensor reading exactly 0.0 gets `b²/c²` (small → **max** weight). The less a sensor sees, the more it
counts.

Reproduced from the committed data — `alberta 2015-03`, day part, reconstructed with the project's own `combine`:

```
   MODIS_A      raw=0      est=0.0       counting_var=1.0     weight=1.0     share=0.481
   MODIS_T      raw=0      est=0.0       counting_var=1.905   weight=0.4662  share=0.224
   VIIRS_SNPP   raw=32     est=6.138     counting_var=0.392   weight=0.6132  share=0.295
   combined y = 1.8098      (published 1.79)
```

The two satellites that saw **nothing** hold **70 %** of the weight; the only satellite that actually saw fire holds
29 %. The published harmonized value is **1.79** where the only observing satellite implies ≈ 6.1 on the Aqua scale.
`se-australia 2025-01` is worse: MODIS_A raw = 0 takes **94.9 %** of the weight (published 3.58).

Scope: **7 months** across the nine committed regions where an active sensor read 0 while another read ≥ 50
(alberta 1, se-australia 1, niger-delta 3, dhaka-kilns 2). Rare, but in each of those months the published value can
be wrong by 3–4× and the 95 % band does not cover it.

**Fix.** `combine` needs the scale factor to compute the pooled-mean variance for the zero case. Change the tuple to
`(value, sigma2_rel, b_over_c, count)` in `science.combine` and in `build._series:281`, then:

```
counting = b_over_c**2 * max(count,1) * (mu/value) if value > 0 else b_over_c * mu
```

(the zero case then gets `b·mu/c`, the same reference point as the others).

### S2 · CRITICAL · the published "harmonized" record is Aqua-dominated, and the step test cannot see the two families disagreeing **[V]**

`server/kw/build.py:229` · `:272-290` · `:293-301` · `:428-437`

```python
to_ref = {REF: ([1.0] * 12, 0.0)}     # build.py:229 — the reference gets EXACTLY zero calibration variance
```

Aqua is the reference *and* carries σ² = 0, so it is the only observer whose variance is not inflated by `mu²·s2`.
Measured Aqua share of the inverse-variance weight (day part, reconstructed from the committed data):

```
punjab        2019:0.75  2020:0.74  2021:0.79  2022:0.74  2023:0.74  2024:0.62  2025:0.58  2026:0.59
se-australia  2019:0.84  2020:0.70  2021:0.62  2022:0.56  2023:0.72  2024:0.66  2025:0.73  2026:0.68
alberta       2019:0.25  2020:0.21  2021:0.36  2022:0.29  2023:0.51  2024:0.38  2025:0.33  2026:0.21
```

Meanwhile the two sensor families have been diverging since 2024. Like-for-like ratio of raw detections, MODIS family
÷ VIIRS family, **on a common month set** (both families coverage ≥ 0.9 — no calibration factors, since the question
is whether the raw detection rates still agree):

```
region            2019   2020   2021   2022   2023   2024   2025   2026
alberta           0.07   0.06   0.12   0.11   0.12   0.09   0.08   0.06
la-rioja          0.12   0.15   0.16   0.18   0.12   0.08   0.09   0.05
n-california      0.14   0.11   0.11   0.14   0.16   0.11   0.09   0.08
parana-delta      0.11   0.11   0.11   0.09   0.11   0.08   0.06   0.06
punjab            0.11   0.11   0.11   0.11   0.11   0.08   0.08   0.05
se-australia      0.08   0.09   0.15   0.11   0.13   0.08   0.07   0.05
dhaka-kilns       0.04   0.03   0.04   0.06   0.06   0.02   0.02   0.01
```

A 30–50 % fall in the MODIS/VIIRS ratio from 2024, in seven of nine regions. (The Method page already lists "MODIS
changes collection (6.03 → 61.03) at the start of 2023; this is listed but not yet step-tested" — the change is
visible here.)

**Why the published diagnostics miss it.** The step test compares `harmonized ÷ aqua_only` (`build.py:430-437`) — a
series that *is* Aqua against Aqua — so it is self-referential and has no power against this failure mode. It reports
"no artificial step" (0.92–1.06) for all four transitions. And the published interval does not widen, because `sigma2`
is a *mean* relative calibration error with no per-period term.

**What I cannot tell from the repo alone:** whether Aqua drifted or the VIIRS chain's 2012–2020 calibration went stale
(or both). Either way the product must not silently pick one family and publish a band that excludes the other.

**Fix (honest, not a rewrite).** (a) Publish the MODIS-only ÷ VIIRS-only ratio per period as a first-class diagnostic
and widen the band by the observed inter-sensor spread. (b) Replace `_drift` with the like-for-like version (S6).
(c) Give the reference a non-zero σ² after a *measured* drift onset rather than hard-coding "Aqua never drifts".

### S3 · IMPORTANT · the "95 % interval coverage = 96 %" headline is a by-construction constant, not a measurement **[V]**

`server/kw/build.py:390` and `:395` · `README.md:86-99`

```python
k = max(1.0, sorted(z)[min(len(z)-1, math.ceil(0.95*len(z))-1)] / 1.96)   # :390
result["ours_seasonal_eb"]["interval_coverage"] = _r(sum(x <= 1.96*k for x in z)/len(z), 3)  # :395
```

`k` is fitted on the **same** 2017–2020 months whose coverage is then reported. With n = 48 the index is
`ceil(45.6)-1 = 45`, i.e. the 46th of 48 → coverage ≡ 46/48 = **0.958** in *every one* of the nine committed
`meta.json` files. That identical value across nine different regions is the signature of a constant.

The honest, unwidened coverage the code actually achieves:

```
alberta       n=48  published 0.958  unwidened 0.583  k=2.785
dhaka-kilns   n=48  published 0.958  unwidened 0.417  k=5.324
la-rioja      n=48  published 0.958  unwidened 0.354  k=4.072
n-california  n=48  published 0.958  unwidened 0.667  k=1.669
niger-delta   n=48  published 0.958  unwidened 0.771  k=1.849
parana-delta  n=48  published 0.958  unwidened 0.792  k=1.892
punjab        n=48  published 0.958  unwidened 0.938  k=1.060
rondonia      n=48  published 0.958  unwidened 0.771  k=2.180
se-australia  n=48  published 0.958  unwidened 0.646  k=2.005
```

The README does disclose that the intervals are "widened to reach 95 % on that test" — but the results table is the

### S4 · IMPORTANT · the "rehearsal" test is too lenient and reports 1.000 for every region **[V]**

`server/kw/build.py:407`

```python
inside = [abs(full[i] - v[i]) <= 1.96 * math.sqrt(var[i]) for i in idx if v[i] is not None and var[i]]
```

`var[i]` is the variance of the **without-SNPP** estimate only, but the quantity tested is the difference of *two*
estimates (with and without SNPP), whose variance is `var_v + var_full`. The test is therefore roughly √2 too lenient.

```
alberta       n=32  inside_interval=1.0  mean_abs_diff_pct=10.0
dhaka-kilns   n=32  inside_interval=1.0  mean_abs_diff_pct=29.5
la-rioja      n=32  inside_interval=1.0  mean_abs_diff_pct=11.1
n-california  n=32  inside_interval=1.0  mean_abs_diff_pct= 5.6
niger-delta   n=32  inside_interval=1.0  mean_abs_diff_pct= 3.8
parana-delta  n=32  inside_interval=1.0  mean_abs_diff_pct= 4.2
punjab        n=32  inside_interval=1.0  mean_abs_diff_pct= 2.2
rondonia      n=32  inside_interval=1.0  mean_abs_diff_pct= 7.9
se-australia  n=32  inside_interval=1.0  mean_abs_diff_pct= 8.9
```

"Withholding Suomi-NPP changes the record by up to 30 %, and 100 % of months still fall inside the interval" is a
silent failure. The web app shows both numbers (`web/src/Record.tsx:377`), so the contradiction is on screen.

**Fix.** `abs(full[i]-v[i]) <= 1.96*math.sqrt(var[i] + var_full[i])` (carry `var` out of the second `_hotspots`
call), and print `mean_abs_diff_pct` next to it.

### S5 · IMPORTANT · the map layer and the area total use different estimators, so the grid does not add up to the record **[R]**

`server/kw/build.py:635-637`

```python
ests = [sum(...beta * count...) / cov[s][i] for s in _active(cov, i)]
val = statistics.fmean(ests) if ests else 0.0        # ← plain mean
```

The area total in `_series` uses `sc.combine` (inverse-variance). Measured on the committed data: punjab 2025-05

### S6 · IMPORTANT · `_drift` compares different month sets across years — the repo's own drift diagnostic is not like-for-like **[V]**

`server/kw/build.py:477-486`

Months are pooled whenever *both* satellites have coverage ≥ 0.9, and the year value is the sum over whatever months
qualified. In 2026 Suomi-NPP loses July (coverage 0.839) and stops on 2026-11-02, so 2026 is a 9-month sum compared
against 12-month sums. Recomputing punjab's `MODIS_A/VIIRS_SNPP` on a **common** month set (Jan–Jun, Aug–Oct):

```
            2021     2022     2023     2024     2025     2026
as published 0.183    0.188    0.197    0.172    0.184    0.131
common months 0.156  0.162    0.118    0.113    0.123    0.131
```

**Punjab's published "2026 drop" disappears entirely** — 0.123 → 0.131 is a rise. The same recomputation for alberta /
la-rioja / se-australia *does* leave a real drop, so the drift is real for some regions — just not for the one a plan
quotes first. Note that the common-month table above (S2) is the same method applied to the two families, and it does
show a real divergence from 2024.

**Fix.** Restrict every year to the intersection of the months used across all years (or publish per-month ratios and
aggregate those), and state the month set in the output.

### S7 · IMPORTANT · "the next four weeks" is computed from the current partial week — it disagrees with the season by one week **[R]**

`server/kw/tools.py:242` vs `server/kw/build.py:578` and `:741`

`tools._next_weeks` takes `b["periods"][-1]`, which is the current **in-progress** ISO week. `build._season` uses the
last **complete** week (`full_weeks[-1]`). On punjab: `periods[-1]` = `2026-W46` (partial), last complete = `2026-W45`
→ `_next_weeks` gives **W47–W50** (skipping the current week), `_season` gives **W46–W49**. The Warning page shows
both numbers side by side and they describe different weeks.

**Fix.** In `tools._next_weeks`, pick the last index with `not b["partial"][i]` (same rule as `build_region:741`).

### S9 · MODERATE · leap-February breaks the month-to-date coverage denominator **[R]**

`server/kw/build.py:507` — `cov = {s: [min(1.0, dmap.get((s,y),0)/D) …]}` divides by `D` = `through.day`. If `through`

## 4. Findings — B. Service layer, API and deployment

### B1 · CRITICAL · a failed email send is silently recorded as delivered → the fire alert is permanently lost **[V]**

`server/kw/alerts.py:278-288` writes `last_notified` / `last_outlook` / `events_seen` **before** `send_now` sends
(`:352`). The code says so itself: `# ponytail: marked before delivery; a failed send is not retried`.

Reproduced locally (alert confirmed, `send_email` mocked to raise):

```
deliver_all -> [{'sent': False, 'error': 'SMTP unreachable'}]
last_notified after the FAILED send -> 2026-11
next poll: triggered = False | already_notified = True
```

The alert now believes it notified the user; every later poll returns `triggered: false` and it is **never retried**.
A fire alert is silently dropped and presented as "nothing new fired" — the exact guardrail the project states.
Only bites once SMTP is configured (it is not, today).

**Fix.** Move the marking out of `check()` into a `_mark(token, …)` called by `send_now` *after* `send_email` returns.
The n8n poll path keeps marking on poll, because n8n sends the mail itself.

### B2 · CRITICAL · confirmation and unsubscribe links are built from an unvalidated `Host` header **[V]**

`api.py:211-212` → `str(request.base_url)` (Starlette derives it from the `Host` header) → `alerts.py:125` (confirm
link) and `:112` (unsubscribe link) in the email sent to the victim.

```
POST /api/alerts   Host: evil.example.com   ->   base_url stored = http://evil.example.com/
```

Anyone can POST an alert with a victim's address and a spoofed Host, and the victim receives an email from the real
app containing a link to the attacker's domain — a phishing primitive against the app's own reputation, amplified by
the "no accounts, the token is the credential" model.

**Fix.** require `PUBLIC_URL` in production; never build links from the request host.

### B3 · CRITICAL · `data/regions/index.json` advertises 6 areas that are not in the repo **[V]**

### B4 · CRITICAL · Docker omits `data/sensor_days.parquet` → one unauthenticated GET triggers a multi-GB re-derivation **[C]**

`Dockerfile:15-17` copies `data/regions/` and `data/global/outlook.json` but **not** `data/sensor_days.parquet`
(146 KB, committed to git, and bundled by `vercel.json`). `data/cache/` is gitignored too, so the image has neither.

Chain on the Docker/HF deployment:

1. `api.py:78` → `tools.refresh_if_stale(rid)` (`tools.py:380`) — `built_at` is 2026-11-10, older than
   `LIVE_TTL_S` (6 h) → starts a background rebuild.
2. `build_region` → `fetch_region` (`firms.py:72`) — no cached years → downloads 2000→2026 for that area.
3. `build_region` → `sensor_days()` (`firms.py:94`) — file missing → re-derives it by scanning

That is a multi-GB download triggered by one unauthenticated `GET /api/regions/{id}/warning`, repeated per area
opened. Even with the parquet copied, the 6-hour TTL means a container started more than 6 h after the build
re-derives it anyway. (Download volume is reasoned from the code path, not measured.)

**Fix.** add `COPY data/sensor_days.parquet data/sensor_days.parquet` to the Dockerfile, and let `sensor_days()`
honour the file's own age rather than the container's (this table only changes when a satellite stops).

### B8 · IMPORTANT · `alerts.create` starts the build before the limit checks; queued builds are unbounded **[C]**

`alerts.py:152` calls `tools.start_aoi(bbox, name)`; the `MAX_ALERTS` / `MAX_PER_EMAIL` / "3 unconfirmed" rejections

Compounding: `_build_slots = Semaphore(2)` (`tools.py:332`) caps **concurrency** but not the **queue**. Unauthenticated,

### B9 · IMPORTANT · evidence and CSV endpoints download FIRMS rows inside the request on Vercel **[V]**

### B10 · IMPORTANT · the outlook rebuild runs inline inside a request, under a global lock **[C]**

`outlook.py:132-145`. `get()` takes `_lock` and calls `build()` inline when the snapshot is older than `max_age_h`.

Where the aggregate is absent (as deployed) `build()` raises `FileNotFoundError` and `get()` silently falls back to
the stale snapshot; `as_of` is shown in the UI, but nothing says the rebuild failed.

**Fix.** build in a background thread (same pattern as `refresh_if_stale`) and serve the current snapshot meanwhile;
surface a `stale` / `rebuild_failed` flag.

### B13 · IMPORTANT · the alerts store is unsafe across uvicorn workers **[C]**

`alerts.py:32` uses a `threading.Lock` — per process. With `--workers N` or two containers on one volume:

- `_load()`/`_save()` are read-modify-write over the whole file → concurrent workers lose each other's alerts.
- `MAX_ALERTS` / `MAX_PER_EMAIL` / "3 unconfirmed" are all bypassable (each worker checks its own snapshot).
- `_save` writes a **fixed** temp name `alerts.tmp` (`:41-43`) → two processes can interleave and corrupt the file →

The docstring acknowledges the single-writer assumption ("one file + one lock; move to SQLite if alerts or writers
grow"), but nothing enforces it.

**Fix.** SQLite (as the comment already suggests); minimally, `flock` the read-modify-write and use a unique temp
name per process.

## 5. Findings — C. Frontend

### C1 · CRITICAL · the "raw" scale turns "no satellite observing" into a real 0 hotspot count **[R]**

`web/src/api.ts:217` — `pick()`'s raw branch returns `b.raw.all_det` (veg) or a sum of `static_det` (static), plain
numbers, never `null`. The weekly block genuinely has nulls: in **every** region `2001-W25`/`2001-W26` have
`hotspots.v = null` and all-sensor coverage `0`. With **Week + "Raw detections"** those two weeks render as a solid
dark cell labelled `0` and the aria-label reads "0 raw detections, all satellites" — while the legend promises a
distinct "no satellite observing" state the raw view never shows.

**Fix.** in `pick()`, return `null` where every `b.coverage[s][i]` is 0; or make `cellStyle`/`ariaFor` test zero
coverage instead of `v === null`.

### C2 · CRITICAL · the "Copy" button crashes the whole app on a non-secure origin **[C]**

`web/src/pages/shared.tsx:73` and `web/src/pages/Connect.tsx:62` —
`navigator.clipboard?.writeText(t).then(…)` guards the property but not the `.then`. `navigator.clipboard` is
`undefined` in any non-secure context (plain `http://` on a LAN IP — a likely local demo setup), so this throws
`TypeError: Cannot read properties of undefined (reading 'then')`. There is **no error boundary** (`main.tsx` renders
`<App/>` bare), so React unmounts the tree → blank page. `Connect.tsx:62` also has no `.catch`, so a rejected
`writeText` is an unhandled rejection.

**Fix.** `const p = navigator.clipboard?.writeText(t); p?.then(ok).catch(noop);`

### C3 · CRITICAL · the Calendar's focus is never reset when Month↔Week is switched; the week grid goes keyboard-dead **[C]**

`web/src/Record.tsx:39` · `web/src/App.tsx:341`

`useState(p.selected)` is initialised once and `<Calendar>` has no `key`, so the state survives a granularity change
(App.tsx:341 only clears `period`).

- **Week view:** `cur = p.focus` is still a month key (`"2026-11"`), so `p.idx.get(cur)` is `undefined` → `onKey`
  returns at `Record.tsx:151` → **arrows/Enter do nothing**, no cell is highlighted, and the `aria-live` readout shows
  "Point at or tab to a cell to read it" instead of the selected period's value.
- **Month view:** `tabIndex={k === start ? 0 : -1}` (`Record.tsx:121`) — `start` is the stale week key, so **no cell
  has tabIndex 0 → the whole table is skipped by Tab**. Same after narrowing the "Years" range while focus sits
  outside it.

**Fix.** `useEffect(() => setFocus(null), [b])` in `Calendar` (or `key={granularity}` on `<Calendar>`).

### C4 · IMPORTANT · WeekGrid up/down arrows are off by one in 53-week ISO years **[R]**

`web/src/Record.tsx:153` — `ArrowUp: -52 / ArrowDown: 52` is applied to the index in `b.periods`, but 2004, 2009,
2015 and 2020 have 53 ISO weeks (`2020-W01` idx 1000, `2021-W01` idx 1053). ArrowDown from 2020-W01 lands on
**2020-W53** (same row, far right) instead of 2021-W01.

**Fix.** step by year/week from the current key, not by a fixed 52.

### C5 · IMPORTANT · no chart exposes its numbers to a screen reader **[R]**

`web/src/Record.tsx:245`, `web/src/Chart.tsx:56`, `web/src/Detail.tsx:161`, `web/src/pages/Warning.tsx:475` — all
charts are `role="img"` + a generic `aria-label`. The values live in SVG paths; the per-point `<title>`s and Chart.tsx's
hover tooltip are mouse-only. `Warning.tsx`'s Weeks chart additionally encodes the percentile in **colour only**.

**Fix.** render a visually-hidden `<table>` of the plotted values next to each chart.

### C6 · IMPORTANT · `role="grid"` on an `<svg>` **[R]**

`web/src/Record.tsx:157` — an `<svg>` cannot host `role="grid"`, and the `<rect>` cells have no `role="gridcell"` and

**Fix.** use the same HTML table structure as `MonthTable`, or drop the grid role and expose the grid as a list.

### C7 · IMPORTANT · a failing `/api/health` puts the entire app into permanent "offline mode" **[C]**

`web/src/App.tsx:70-74` — `api.health().then(…).catch(() => setOnline(false))`. If health 404s (older server —

### C8 · IMPORTANT · the URL is written with `history.replaceState` and nothing listens to `hashchange` **[R]**

`web/src/App.tsx:87-101` — every state change overwrites the hash, so the browser Back button leaves the site instead

### C9 · MODERATE · a seeded analyst question is silently discarded **[R]**

`web/src/Analyst.tsx:148-150` — `if (p.seed) { send(p.seed); p.onSeedUsed(); }`. `send` returns early when `busy`, but

### C10 · MODERATE · stale `onMonth` closure during the timeline timelapse **[R]**

`web/src/App.tsx:163-177` — `doSearch` awaits `nominatim.openstreetmap.org` with no `AbortController` and no

**Fix.** add a busy state and an `AbortSignal.timeout(8000)`.

## 6. Scientific risk (disclosed, but worth stating plainly)

The largest risk is **not** a bug:

- **The 95.8 % interval coverage is reached by construction** (S3). The conformal widening `k_scale`
  (`build.py:389-395`) is fitted on the same 2017–2020 hold-out it is then scored on. The README and Method page say
  so ("intervals are widened to reach 95 % on that test"), but the results table's "96 %" column reads as a
  measurement, and the pre-widening coverage is 35–94 %.
- **The published record is Aqua-dominated and the two sensor families disagree from 2024** (S2), and the step test
  cannot see it because it compares Aqua against Aqua. The Method page does list the MODIS collection change
  (6.03 → 61.03, start of 2023) as "not yet step-tested", and Aqua's post-2021 drift as a limitation — but the
  divergence itself is not published, and the interval does not widen for it.
- **The "no artificial step" result is partly self-referential** (S2, S5): `harmonized ÷ aqua_only` compares a
  series that *is* Aqua to Aqua.
- **Seven months in the committed regions have a published value dominated by sensors that observed nothing** (S1).
- **Four of nine areas fall outside their placebo step range** (`docs/readme/numbers.json` → `steps[].inside`):
  South-east Australia, Rondônia, Punjab, Northern California. Punjab under-corrects by ~7 %; Paraná Delta's denial
  bias is +27.5 %.
- **No cloud-cover denominator**; cloudy months read low for every satellite alike.
- **The early-warning rule has not been backtested**, and the outlook's Aqua-only orbit drift since 2022 is
  acknowledged but not corrected.
- **Persistent heat sources are not validated against an independent kiln inventory** — correctly labelled "likely".

The last four are already published by the project (README "Where it still falls short", Method page "Known
limitations"), which is the right call. The first three are **not** currently published in that form.
